## 3. 两次上传失败的原因（已定位）

| 次序 | 上传的包 | 依赖 | 结果 |
|---|---|---|---|
| 1 | FINAL_v1 初版 | `torch==2.14.1`（PyPI 版） | exit code 1 |
| 2 | FINAL_v1 重建版 | `--extra-index-url` + `torch==2.14.1+cpu` | **仍 exit code 1** |

**第 1 次是可确证的本地缺陷**：按提交的 requirements 解析，评测机要装 **29 个包**，
含 `torch-2.14.1` 的 554.6 MB CUDA 轮子与 `cuda-toolkit 13`、cudnn/cublas/nccl/triton 整套 CUDA 栈
（我用的是本地手动装好的 `+cpu`，**验收的制品与交付的制品不一致**）。

**第 2 次说明修正方向仍不成立**：依赖已解析为 10 个包、零 CUDA，
但评测机显然**不认 `--extra-index-url`（或访问不到 download.pytorch.org）**。
至此，任何把 torch 放进 `requirements.txt` 的做法在本赛事都不可靠。

**旁证**：唯一成功过的 `strong_baseline_v1` 用的正是纯 PyPI 树模型依赖——与 TREE_v1 同类。

**结论：提交包不得依赖 torch。** 这条已写死为项目约束。

## 4. TREE_v1 的选型依据

去掉 torch 后，能保留 IC 的空间是有限的，我按证据而不是偏好选：

| 实验 | 结果 | 结论 |
|---|---|---|
| sklearn MLP 替代 TabM | DEV19 外层 IC **0.044725**（TabM 同窗 0.081463） | 否掉，替代不了 |
| 纯树候选上限 | DEV 0.081645（c1 单体）～0.080688（l3+c1） | TabM 的 +0.0031 树模型做不到 |

在纯树集合内按 §12.1「近似平局 → 先比最差年度 → 再取更简单」比较：

| 候选 | DEV 合并 | 最差 DEV 年度 | 结论 |
|---|---|---|---|
| c1 单体 | 0.081645 | 0.081136 | DEV 略高，但最差年度更低 |
| **l5 + c1** | 0.081559 | **0.081258** | **选中**（DEV 只差 0.000086，最差年度更好） |
| l3 + c1（ALT_v1） | 0.080688 | 0.079875 | 略低 |

**TREE_v1 = 0.5 × LightGBM L5（3 种子）+ 0.5 × CatBoost C1（3 种子）**，
每日先各自逐日秩、按种子取均值，再 0.5/0.5 融合，最终输出再 rank。
轮数按预登记规则取三折中位数：L5 = 311 轮、CatBoost C1 = 875 棵。

## 5. 验证状态（做到哪一步就写哪一步）

| 检查项 | strong_baseline_v1 | FINAL_v1 | ALT_v1 | **TREE_v1** |
|---|---|---|---|---|
| 本地完整验收（场景/不变性/成员等价/时序） | 部分（旧流程） | 通过 | 通过 | **通过** |
| **干净 venv 按交付 requirements 安装** | 未做（当时无此项） | 本地通过（评测机失败） | 未单独做 | **通过（19 包，无 torch）** |
| 干净环境加载 + 预测 | — | 本地通过 | 通过 | **通过（普通日 + 2 日短历史）** |
| 重复调用 / 股票置换 / 删未来行 | — | 一致 | 一致 | **一致（置换差 0.0）** |
| `train.py` 独立复跑 | 通过 | 通过（差 0.0） | 实测通过（差 ≤5e-11），但存在线程数不一致的**未验证风险**，见下 | **通过（6 个模型差 0.0，排序一致）** |
| 平台真实入口 `submission_dir` 烟雾 | 通过 | 通过（7 日 2,100 行） | 通过（7 日 2,100 行） | **未单独跑**，见 §8 |
| 禁网 / 无 CUDA / 静态导入 / 无 sys.modules | ❌ 有 `sys.modules` 注册 | 通过 | 通过 | **通过** |

**本轮发现并已修的缺陷**：首次复跑 TREE_v1 时，LightGBM `l5_seed20261005` 与随包模型不一致
（max abs 3.3e-2、排序不同）——原因是随包模型用 **6 线程**训练、`train.py` 默认 **8 线程**，
LightGBM 跨线程数不保证位一致。已把 `train.py` 默认线程固定为 6，重跑后 6 个模型全部 **差 0.0**。

**仍未修的同类缺陷**：`ALT_v1` 的 `train.py` 默认 8 线程、随包模型是 6 线程，
与 TREE_v1 出问题的那次是同一种不一致。当时对该包实测误差只有 ≤5e-11（未触发分歧），
但既然同类不一致在 TREE_v1 上已出现过 3.3e-2 的真实分歧，**若最终改用 ALT_v1 上传，
必须先按同样方式固定线程数并重验**，不能因为它当次侥幸通过就默认安全。
